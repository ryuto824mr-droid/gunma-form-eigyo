# 外から送信だけの処理を呼ぶ手順(段階1: 平日に1日2回)

送信待ちの送信だけを行う処理 `GET /api/crm?action=run-send-queue` を、GitHub Actions から平日に1日2回呼ぶための手順。
雛形は `docs/ops/send-queue.workflow.yml.example`。

## 先に知っておくこと

- **呼ぶと実際に送信される。** 送られるのは送信待ち(pending)の行だけ。保留(on_hold)の行は送られない
  (保留からの自動の移し替えは、設定 `auto_release_hold` が「入」のときだけ)。
- **1日の上限は `daily_send_limit`(設定)で決まる。** 呼ぶ回数を増やしても、上限を超えては送られない。
  上限は、失敗した送信も含めて「今日の送信記録の件数」で数える。上限の値は管理者が決めて設定で変える。
- 土日・祝日は、送信の処理の中で自動で休む(設定 `skip_weekends_holidays`)。
- 企業探し・予約送信は、この処理では動かない(毎日の処理 18:00 で動く)。
- 鍵(`CRON_SECRET`)が無い・違う呼び出しは、401 で何もせずに断られる。

## 1. CRON_SECRET を決めて、Vercel と GitHub の両方に登録する

Vercel に登録済みの `CRON_SECRET` は「機密(sensitive)」のため、画面でも API でも**値を読み出せない**。
GitHub にも同じ値を登録する必要があるので、**新しい値を作って両方に登録し直す**。

1. 新しい値を作る(手元で1回だけ。表示された値は、この手順の間だけ使い、どこにも保存しない)
   ```
   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
   ```
2. Vercel: プロジェクト `gunma-form-eigyo` → Settings → Environment Variables → `CRON_SECRET`(Production)を編集し、
   1 の値に置き換えて保存する。種類は「Sensitive」のまま。
3. **Vercel を再デプロイする。** 環境変数の変更は、新しいデプロイから効く(Deployments → 最新の本番 → Redeploy)。
   - 再デプロイが終わるまでは古い値が効いている。毎日の処理(18:00)の前に終わらせる
   - Vercel の cron(毎日の処理・返信の確認)は、新しい値を自動で使う(設定の変更は要らない)
4. GitHub: リポジトリ → Settings → Secrets and variables → Actions → New repository secret
   - Name: `CRON_SECRET`
   - Secret: 1 の値
5. 1 で表示した値は、画面やメモから消す。

## 2. workflow を置く(この時点から自動で動き始める)

1. `docs/ops/send-queue.workflow.yml.example` を `.github/workflows/send-queue.yml` にコピーする。
2. 時刻を確かめる(UTC で書く。日本時間 - 9時間)。雛形は平日の 日本時間 10:30 と 14:30。
3. main に push する。GitHub の定時実行は、main(既定のブランチ)にある workflow だけが動く。
4. 最初の確認は、**送信待ちが0件のときに**、Actions の画面から「Run workflow」で手動実行するのが安全
   (送るものが無いので、鍵が通ること・処理が動くことだけを確かめられる)。
   記録に `"send_queue":{"processed":0,...}` のような結果が出れば正常。`401` なら鍵が違う。

## 3. 止めるとき

- すぐ止める: GitHub → Actions → send-queue → 右上の「…」→ Disable workflow
- 送信そのものを止める: 送信待ちの行を保留にする(「あとで送る」画面)か、`daily_send_limit` を下げる
- 鍵が漏れたかもしれないとき: 1 の手順で `CRON_SECRET` を新しい値に替える(Vercel と GitHub の両方)

## 4. 回数を増やすとき(段階2以降)

- 雛形の `cron` の時刻を足す(例: `"30 0-7 * * 1-5"` で 日本時間 9:30〜16:30 に毎時、8回)。
- 先に `daily_send_limit` を段階に合わせて上げる(段階1: 30 → 段階2: 50 → 段階3: 75 → 段階4: 100)。
- 段階3(1日75件)あたりから、Vercel Hobby の CPU の枠(月4時間)を超える見込み。Pro への移行を先に決める。

## 注意

- 非公開のリポジトリの Actions は、月2,000分まで無料。1回の実行は約5分(送信の処理を待つため)。
  1日2回 × 平日22日 × 5分 = 約220分。
- 公開のリポジトリで60日間 push が無いと、GitHub が定時実行を止めることがある。

## 5. 企業探しだけの処理を平日の朝に呼ぶ(run-discover)

送る企業を増やすため、企業探しとリサーチだけを行う処理 `GET /api/crm?action=run-discover` を、
GitHub Actions から平日の日本時間 6:05・8:05 の2回呼ぶ。雛形は `docs/ops/discover.workflow.yml.example`。

### 先に知っておくこと

- **送信はしない。** 企業探し(Brave・Google Places)とリサーチ(相手のサイトを開く)を行い、新しく見つけた企業を
  **保留(on_hold)** で積むだけ。送信・予約送信・送信待ちの処理は動かない。
- **外部の API の費用がかかる。** 1社あたりの目安は、検索と AI の判定を合わせて約1円
  (2026-10 の全国の試験: 30回の検索・237社のリサーチで約270円)。
- **1日に調べる数の上限:** 1プロジェクトあたり `discover_daily_limit`(設定。未設定なら40社)。
  今日の自動パイプラインの記録の「調べた数」の合計で数え、18:00 の毎日の処理の分も含む。
  1回に調べる数は、自動パイプラインの設定の「1日の上限」(daily_limit。初期12・最大15)まで。
- 1回の実行は最大約280秒。2つのプロジェクトで半分ずつ使う。自動パイプラインが「切」のプロジェクトは何もしない。
- 土日・祝日(日本時間)は何もしない。
- 鍵(`CRON_SECRET`)は送信の workflow と同じものを使う。

### 設置の手順

1. `CRON_SECRET` が GitHub の Secrets に登録されているか確かめる(リポジトリ → Settings → Secrets and variables → Actions)。
   - 無ければ「1. CRON_SECRET を決めて、Vercel と GitHub の両方に登録する」を先に行う。
   - Vercel の値を作り直すと、登録済みの送信の workflow も新しい値に揃える必要がある。
2. `docs/ops/discover.workflow.yml.example` を `.github/workflows/discover.yml` にコピーする。
3. **17:30〜19:00(毎日の処理の前後)を避けて** main に push する。push した時点から定時実行が有効になる。
4. 最初の確認は、平日の昼に Actions の画面から「Run workflow」で手動実行する。
   - 記録に `{"skipped":false,"results":[{"project":"locle","enabled":false},{"project":"ozukanzukan",...,"researched":N,...}]}` が出れば正常。
   - `401` なら鍵が違う。`"skipped":true,"reason":"土日"` なら休みの日。
   - 送信管理の画面の「自動パイプラインの記録」に1行増え、「あとで送る」の保留が増える(送信待ちは増えない)。
5. 翌朝の 6:05・8:05 の2回が動いたことを、Actions の記録と「自動パイプラインの記録」で確かめる。

### 止めるとき

- すぐ止める: GitHub → Actions → discover → 右上の「…」→ Disable workflow
- 調べる数を減らす: `discover_daily_limit` を下げる(0 にすると、朝の処理は何も調べない。18:00 の毎日の処理には効かない)。

### 注意

- **Vercel Hobby の CPU の枠(月4時間)に気をつける。** 企業探しはサイトをブラウザで開くため、送信よりも CPU を使う。
  1回約280秒 × 2回 × 平日22日 ≒ 月約3.4時間(実際に動いている時間。CPU の時間はこれより短い)。
  設置後1週間は Vercel → Usage の「Fluid Active CPU」を見る。枠を超えそうなら、回数を減らす(6:05 の1回にする)か Pro に移る。回数を増やすのも、Usage に余裕があることを確かめてから。
- GitHub Actions の時間: 1回約5分 × 2回 × 22日 ≒ 月220分。送信の workflow(月約220分)と合わせても、非公開のリポジトリの無料の枠(月2,000分)に収まる。
- 1日の数え方: 1日に調べる数の合計は、DB の日付(`CURRENT_DATE`)で数えている。DB の時刻が UTC のままだと、
  日本時間の 6:05・8:05 の2回は「前の日」の分として数えられる(1日の上限が実際より緩くなる)。DB の時刻の設定を確かめてから上限を決める。
